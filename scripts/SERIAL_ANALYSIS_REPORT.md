## 2. Expected behavior: reset when barcode day changes

All other 0001s occur when the **day in the barcode** changes (e.g. A27… → A28…). Examples:

- 2026-01-27 19:08: A27A26B0026 → **A28**A26**A0001** (day 27→28, B→A, 0001 ✓)
- 2026-01-28 19:04: A28A26B0036 → **A29**A26**A0001** (day 28→29, B→A, 0001 ✓)
- 2026-01-30 21:36: A30A26A0044 → **A31**A26**A0001** (day 30→31, 0001 ✓)
- 2026-01-31 18:50: A31A26C0122 → **A01**B26**A0001** (day 31→01, C→A, 0001 ✓)
- Similar pattern on Feb 2–12: each first 0001 of the day is when barcode day rolls.

So:

- **"SAME_DAY_RESET"** (11) and **"RESET_ON_SHIFT_CHANGE"** (12) in the script mostly refer to the **same** transitions: new barcode day + shift B or C → A, with serial 0001. That is **correct** behavior, not a bug.
- Your "day" for the barcode appears to roll around **~19:00–21:00 UTC** (e.g. 7–9 PM), so calendar date in UTC can still be the "previous" day when the barcode already shows the next day.

## 4. What the data suggests is wrong in the logic (NOW FIXED)

- **Reset condition:** For at least one case (2026-02-13 01:54:28), the system decided to reset to 0001 even though:
  - The barcode day (13) and shift (A) did not change, and
  - The previous serial for that context was 44.
- **Root causes:**
  - **Per-model last record:** Last record for current model not found (e.g. filter by `ModelNumber` or config), so code assumed "no record today" and reset.
  - **Config / modelSerialConfig:** Missing or wrong `modelSerialConfig` (or equivalent) for that model at that time, leading to "new model" or "missing config" reset.

### FIX APPLIED (in `services/serialNumber.js`)

1. **Once-per-day guard:** Track `lastResetDate` and only allow **ONE** reset per calendar day. If we've already reset today (checked both in-memory and in DB `modelSerialConfig.lastReset`), no second reset is allowed regardless of any other condition.

2. **Recovery from records:** When `modelSerialConfig` is missing or has invalid `currentValue`, instead of resetting to 0001/starting serial, the code now queries the last record in the records collection for this model and continues from there (lastSerial + 1).

3. **Persisted guard:** The `lastReset` timestamp is stored in `modelSerialConfig` and checked on every call, so the once-per-day guard survives server restarts.
